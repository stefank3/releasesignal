# Release Signal V1.2 Demo Story Flow

This document defines a small presentation-ready demo story for Release Signal V1.2.

It is documentation-only. It does not add a runtime demo mode, seed data, parser behavior, prompt behavior, upload behavior, execution evidence behavior, artifact contracts, review scoring, or Release Readiness semantics.

## Demo Purpose

Use this demo to show Release Signal as a sprint-planning and release-readiness assistant, not only as an AI test case generator.

The story should demonstrate how Release Signal Standard Trial can help QA and engineering teams move from weak sprint input toward:

- clearer sprint-ready requirements
- better test coverage
- earlier risk visibility
- review-driven test improvement
- execution evidence
- release-readiness assessment

The core positioning is:

```text
Sprint Planning -> Requirement Refinement -> Test Design -> Coverage Review -> Generate from Gaps / Improve -> Execution Evidence -> Release Readiness
```

Release Readiness remains the primary release-decision signal and is derived from structured artifacts and deterministic rules.

## Weak Jira-Style Starting Story

Paste this story into Release Signal as the starting requirement:

```text
As a workspace member, I want to upload a CSV file with test execution results so that Release Signal can show execution evidence for my test suite.
```

Weak acceptance criteria:

- User can upload a CSV file.
- System validates the file.
- Results are shown in the workspace.
- Invalid files show an error.

This story is intentionally weak. It is specific enough to generate useful QA output, but it leaves important implementation and testing questions unanswered.

Missing detail to look for during the demo:

- file format details
- required columns
- allowed execution statuses
- invalid or malformed file behavior
- case ID matching rules
- partial success behavior
- duplicate row behavior
- empty file behavior
- authorization boundaries
- suite version expectations
- expected Release Readiness impact

## Demo Flow

1. Paste the weak story.

   Explain that this starts before sprint work begins. The team has a real story, but it is not yet testable enough for confident delivery.

2. Refine the requirement.

   Use Requirement Refinement to turn the weak story into a more testable requirement with scope, acceptance criteria, risk areas, negative paths, and open questions.

3. Generate tests.

   Generate a structured test suite from the refined requirement. Position this as test design support, not as the whole product value.

4. Review the suite.

   Run the review step to identify coverage gaps, weak diagnostics, missing risk coverage, and unclear expected results.

5. Improve from review gaps.

   Use Generate from Gaps or Improve Test Plan to strengthen the suite from the review findings. The goal is to show review-driven test improvement rather than one-shot test generation.

6. Export the execution template.

   Export the execution template for the current suite. Explain that execution evidence is separate from test design quality.

7. Upload sample execution results.

   Upload a small CSV result set prepared from the exported template. Keep this as a presenter-prepared demo artifact unless a future scoped branch adds official fixtures.

8. View Execution Evidence.

   Show how execution results are captured as structured execution evidence without mutating the test suite or review score.

9. View Release Readiness.

   Show Release Readiness as the final demo signal. Emphasize that it is derived from the current requirement, test suite, review result, and execution evidence through deterministic rules.

## Demo Boundaries

Be explicit about these boundaries during the presentation:

- This is not a Jira integration.
- This is not live automation execution.
- This is not a TestRail, Qase, Xray, or Zephyr integration.
- This is not a payment, billing, credit, or subscription demo.
- This does not change Release Readiness semantics.
- This does not claim defect-free releases.
- This does not introduce runtime demo data.
- This does not change upload behavior or execution evidence parsing.
- This does not change artifact contracts.

## Optional Sample Execution CSV Notes

If sample data is used, keep it presenter-prepared and documentation-only. Do not add fixtures or seed data unless a later scoped branch approves that behavior.

Suggested shape after exporting the execution template:

```csv
caseId,status,source,notes
TC-001,passed,manual,Happy-path upload accepted
TC-002,failed,manual,Malformed CSV did not show a clear enough error
TC-003,blocked,manual,Authorization scenario needs test account setup
```

Use only case IDs that exist in the generated suite or the exported execution template for the live demo. If the generated suite uses different case IDs, update the presenter-prepared CSV before uploading.

The sample result mix should show why Release Readiness is useful:

- passed results demonstrate successful coverage
- failed results create visible risk
- blocked results show unresolved execution constraints
