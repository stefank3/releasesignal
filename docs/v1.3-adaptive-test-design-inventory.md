# V1.3 Adaptive Test Design Inventory

Branch: `feature/v1.3-adaptive-test-design-inventory`

Status: inventory only

## Purpose

V1.3 starts with intent-aware technical requirement refinement for Release
Signal.

The first implementation target is improving how raw technical input becomes a
`RefinedRequirement` while preserving executable technical detail. Adaptive Test
Design and Test Design Intent Detection are supporting mechanisms for that
requirement-refinement goal, not the first product surface.

Test generation alignment is downstream after the requirement artifact is
stronger. Review alignment comes after requirement and generation behavior are
improved. Optional intent metadata or a `TestDesignIntentArtifact` comes later
only if explicitly approved.

The product problem is that detailed technical input can collapse into generic
QA language. Examples include outputs such as:

- Verify CRUD operations with valid and invalid inputs.
- Verify error handling and data integrity.
- Verify authorization and idempotency.

That is not enough when the source input contains concrete executable detail:
endpoints, HTTP methods, headers, request bodies, schemas, status codes,
response fields, roles, UI fields, file columns, validators, modules, business
rules, boundary values, and state transitions.

Main V1.3 rule:

```text
Release Signal must not summarize away executable technical detail.
```

Architecture rule:

```text
AI -> parsed -> structured artifacts -> deterministic system logic -> UI
```

This branch does not implement behavior, change prompts, alter parser behavior,
change artifact contracts, redesign review scoring, or change Release Readiness
semantics.

## Supported Intent Direction

Future V1.3 work should consider these test design intents:

- API testing
- Contract testing
- UI functional testing
- Unit testing
- Regression testing
- Smoke testing
- Integration testing
- Data validation testing
- Security / RBAC testing
- End-to-end workflow testing
- File import/export testing
- Accessibility/basic usability testing
- Basic performance/reliability testing

A requirement may have a primary intent and secondary intents. Example:

```text
Primary intent: API_CONTRACT
Secondary intents: SECURITY_RBAC, REGRESSION, DATA_INTEGRITY
```

The intent signal must not become product truth if it is only prompt text. If
intent later influences system behavior, it should be parsed, validated,
normalized, and either represented in an approved structured artifact or used as
bounded deterministic context.

## Current Requirement Refinement Flow

Relevant files:

- `app/api/chat/route.ts`
- `lib/server/chat/promptBuilder.ts`
- `lib/framework/systemPrompt.ts`
- `lib/server/chat/modelResponseParser.ts`
- `lib/server/chat/coachFlowService.ts`
- `lib/server/chat/coachFormatting.ts`
- `lib/server/chat/artifactUpdateService.ts`
- `lib/server/chat/artifactPersistence.ts`
- `lib/chat/artifact.ts`

Current flow:

1. The user provides free-form input through the chat workspace.
2. `app/api/chat/route.ts` parses request state and decides the execution path.
3. `buildPromptPayload` in `lib/server/chat/promptBuilder.ts` chooses the coach
   prompt when `wantCases` is false and `executionMode` is `coach`.
4. `QA_SYSTEM_PROMPT` in `lib/framework/systemPrompt.ts` asks for locked JSON
   with objective, context, inScope, outOfScope, integrations,
   acceptanceCriteria, and riskFocus.
5. `parseRefinedRequirementResponse` in
   `lib/server/chat/modelResponseParser.ts` extracts and normalizes the model
   output into a structured requirement shape.
6. `runCoachFlow` formats the visible technical requirement from the persisted
   artifact, not from free-form model prose.
7. `mergeArtifact` and persistence helpers in `lib/chat/artifact.ts` and
   `lib/server/chat/artifactUpdateService.ts` normalize and persist the
   requirement artifact.

Prompt construction points:

- `QA_SYSTEM_PROMPT` defines the primary coach behavior.
- `buildCoachModeInstruction` adds mode-specific rules and schema reminders.
- `artifactToContextText` adds persisted artifact context when continuity is
  active.
- `buildWorkflowActionMessage` in `app/api/chat/route.ts` creates special
  messages for artifact-driven actions such as `refine_requirement`.

Parser expectations:

- Coach output must be JSON.
- Requirement-like output must normalize into a `NormalizedRefinedRequirement`.
- A requirement needs an objective and enough section signal to persist.
- The parser deterministically derives missing business rules, edge cases,
  non-functional constraints, coverage targets, minimal repro scenarios, and
  open questions from available fields.

Where technical detail may be lost:

- The current coach schema has no explicit fields for API endpoints, HTTP
  methods, headers, request bodies, schemas, UI selectors, file columns,
  modules, functions, or validators.
- `normalizeRequirementLike` may derive generic business rules and edge cases
  from broad acceptance criteria. Some fallback logic is still domain-shaped
  around payment, email, fulfillment, and order-style examples.
- `artifactToContextText` slices many lists to 12 items, which is usually safe
  for compact context but can drop long technical inventories.
- `buildCoachModeInstruction` emphasizes ambiguity, risks, negative paths, and
  bounded assumptions, but it does not explicitly tell the model to preserve
  executable details by category.
- Valid happy paths can be pushed into `edgeCasesNegativePaths` if the model
  frames concrete operations as "edge" work.

## Current Test Generation Flow

Relevant files:

- `app/api/chat/route.ts`
- `lib/server/chat/promptBuilder.ts`
- `lib/framework/systemPrompt.ts`
- `lib/server/chat/postModelFlowService.ts`
- `lib/server/chat/casesFlowService.ts`
- `lib/server/chat/testSuiteService.ts`
- `lib/server/chat/reviewGapPromptContext.ts`
- `lib/chat/artifact.ts`

Current flow:

1. The user can generate tests in cases mode or use artifact-driven workspace
   actions.
2. `buildPromptPayload` selects `CASES_SYSTEM_PROMPT` when `wantCases` is true.
3. The cases prompt requires strict plain text test cases, not JSON.
4. `buildCasesModeInstruction` adds continuity rules, duplicate avoidance, and
   risk-focused generation pressure.
5. `buildWorkflowActionMessage` creates more specific action messages for:
   `generate_tests_from_requirement`, `generate_next_batch_of_tests`, and
   `regenerate_suite`.
6. `runPostModelFlow` delegates cases output to `runCasesFlow`.
7. `parseGeneratedTestCases` parses strict `TC-XXX` blocks into
   `TestSuiteArtifact` cases.
8. `persistGeneratedSuiteArtifact` normalizes and persists the suite.

Generated suite format:

```text
TC-XXX - Title

Type: Positive | Negative | Edge | Security
Priority: High | Medium | Low

Preconditions:
...

Test Steps:
...

Expected Result:
...

Tags:
...

Notes:
...
```

Parser expectations:

- Each case must include Type, Priority, Preconditions, Test Steps or Steps, and
  Expected Result or Expected Results.
- `TestCase.type` only persists enum-safe values: `UI`, `API`,
  `Integration`, or `E2E`.
- `Positive`, `Negative`, `Edge`, and `Security` remain body text today, not
  structured artifact enum values.
- `Priority: High | Medium | Low` remains body text today unless the model uses
  `P0`, `P1`, or `P2`.

Where intent could influence output:

- The cases system prompt could instruct API, contract, UI, unit, file, RBAC, or
  regression-specific case structure.
- `buildWorkflowActionMessage` could include detected intent context for
  artifact-driven actions.
- `reviewGapPromptContext` already safely adds current review gaps when the
  review matches the current suite version; a similar bounded helper could add
  current test design intent context later.
- `testSuiteService` could later receive deterministic intent metadata to guide
  validation or traceability, but this would require approved scope.

Where technical detail may be lost:

- The strict test case format is generic across all domains.
- There is no dedicated unit-test case format for module/function/input/output
  behavior.
- There is no dedicated API contract case format for endpoint, method, headers,
  content type, request schema, response schema, and status code.
- There is no dedicated file import/export format for file type, required
  columns, mappings, malformed rows, and error messages.
- The prompt asks for a balanced mix across Positive, Negative, Edge, and
  Security, but it does not define that valid happy-path operations are positive
  core workflow coverage, not edge coverage.
- The parser can accept a test case whose body preserves technical detail, but
  it does not enforce or inspect intent-specific detail completeness.

## Current Review Flow

Relevant files:

- `app/api/chat/route.ts`
- `lib/server/chat/postModelFlowService.ts`
- `lib/server/chat/reviewFlowService.ts`
- `lib/domain/deterministicReviewService.ts`
- `lib/server/chat/reviewExplanationService.ts`
- `lib/server/chat/reviewGapPromptContext.ts`
- `lib/server/chat/artifactUpdateService.ts`
- `lib/framework/reviewSchema.ts`

Current flow:

1. Review can be triggered through review mode or `review_test_suite`.
2. Standalone pasted review input can be ingested into artifacts before review.
3. `runReviewFlow` builds the authoritative review result deterministically
   from `RefinedRequirement` and `TestSuiteArtifact`.
4. AI review JSON is no longer authoritative for scoring.
5. Optional review explanation is supplemental only and does not change review
   truth.
6. `persistReviewArtifact` stamps review lineage with requirement and suite
   versions.

Deterministic review/scoring boundaries:

- Review score measures test design quality only.
- Execution evidence does not change the review score.
- Review reads structured requirement units and structured suite cases.
- Review uses token overlap and phrase signals, not free-form model judgment.
- Review units currently come from acceptance criteria, functional scope,
  business rules, and edge cases.

Where review treats coverage generically:

- `RequirementUnit.source` is limited to acceptance criteria, functional scope,
  business rules, and edge cases.
- There is no intent dimension such as API, contract, unit, file import/export,
  or RBAC.
- Coverage strength is based on token matching and phrase signals, so precise
  technical details can matter only if they survive as requirement unit text and
  case text.
- `buildLevelAndScopeScore` checks broad scenario signals using keywords for
  positive, negative, edge, and security coverage.
- The review does not currently know whether a suite is supposed to be API
  contract testing, unit testing, UI functional testing, or mixed intent.

Where intent-aware review context could be added safely:

- A future bounded helper could produce review context from existing structured
  requirement/suite text without changing scoring.
- A future deterministic intent helper could classify source text and expose
  primary/secondary intent only as non-authoritative context first.
- Intent-aware scoring should not be added without explicit approval because it
  would change review semantics.

## Technical Detail Preservation Risks

API / contract details:

- Endpoint, method, headers, content type, request payload, query parameters,
  response fields, status codes, and schema constraints have no dedicated
  requirement artifact fields today.
- Generic risk prompts may turn concrete API operations into broad CRUD
  language.
- Valid API operations such as `POST` with a valid payload or `GET` by valid ID
  can be misplaced into edge/negative sections if the prompt does not forbid it.

UI details:

- Screens, fields, buttons, user actions, validation messages, and visible state
  changes may be flattened into general "verify UI" wording.
- No current requirement field separates core UI workflow from UI validation
  messages or accessibility/usability concerns.

File import/export details:

- File formats, required columns, optional columns, malformed files, mapping
  rules, duplicate rows, and export headers can be lost unless preserved in
  acceptance criteria or business rules.
- Execution CSV upload has deterministic parsing, but that is execution
  evidence, not test design intent.

Unit testing details:

- Modules, functions, inputs, outputs, branches, validators, mappers, reducers,
  and mocked dependencies have no dedicated requirement artifact fields.
- Current cases format is workflow-style and may not naturally express unit
  tests with isolated inputs/outputs.
- Valid branch behavior can be mislabeled as edge coverage.

Regression and smoke details:

- Regression scope can collapse into "verify no regression" without naming
  preserved behavior.
- Smoke coverage can become too broad if critical path, environment, and
  non-mutating constraints are not preserved.

RBAC / security details:

- Roles, permissions, unauthenticated access, forbidden access, ownership checks,
  and tenant boundaries should remain explicit.
- Security can be over-generated as generic auth testing if source-specific
  roles and resource ownership details are lost.

## Happy Path Vs Edge / Negative Classification Risks

Current prompt and structure risks:

- `CASES_SYSTEM_PROMPT` asks for a balanced mix across Positive, Negative, Edge,
  and Security but does not define which operations are positive core workflows.
- The requirement artifact has `edgeCasesNegativePaths` but no explicit
  `positiveFlows` or `coreWorkflows` field.
- `normalizeRequirementLike` can derive edge cases from risks and criteria when
  explicit edge/negative paths are absent.
- Deterministic review includes `edgeCases` as requirement units but does not
  distinguish whether a requirement unit was actually a valid happy path that
  was placed in the wrong section.

API examples that must remain positive/core workflow coverage:

- `POST` with valid payload.
- `GET` by valid ID.
- `PATCH` with valid payload.
- `DELETE` with a valid soft-delete request.

Unit examples that must remain positive/core workflow coverage:

- Valid input returns expected output.
- Supported enum/value follows expected branch.
- Known validation rule passes correctly.

True edge/negative examples:

- Missing required fields.
- Invalid data types.
- Malformed ID.
- Unsupported filter.
- Invalid pagination.
- Duplicate transaction ID.
- Unauthorized or forbidden access.
- Invalid content type.
- Unsupported patch field.
- Repeated delete after soft deletion.
- Null or undefined input.
- Empty collection.
- Boundary value.
- Dependency failure.
- Thrown validation error.
- State conflict.
- Malformed file.
- Missing required column.
- Invalid mapping.

## Possible Safe V1.3 Attachment Points

Prompt-only hardening:

- Add explicit anti-generic and detail-preservation rules to coach and cases
  prompts.
- Add happy-path classification rules to coach and cases prompts.
- Add intent-specific output guidance while preserving existing JSON and TC text
  contracts.
- Risk: prompt-only behavior is not inspectable or deterministic.

Deterministic helper/service layer:

- Add a small intent detection helper that scans source text for explicit
  technical signals.
- Keep the helper pure and testable.
- Example signals: HTTP method + path, JSON schema fields, UI action vocabulary,
  function/module names, file column names, RBAC role words.
- Initial helper output should be advisory unless explicitly approved as
  artifact truth.

Lightweight metadata:

- Future approved work could store intent metadata alongside a requirement or
  future artifact.
- This should not be smuggled into existing contracts in V1.3.0.
- Any persistence change needs explicit human approval and compatibility review.

Review-context helper:

- A bounded helper could produce text context such as "Current detected test
  design intent: API_CONTRACT" for generation/review prompts.
- It should not alter scoring until explicitly approved.
- It should avoid stale or unversioned context issues, following the pattern in
  `reviewGapPromptContext`.

Optional future `TestDesignIntentArtifact`:

- Could hold primary intent, secondary intents, detected signals, confidence,
  source excerpts, and open questions.
- Should be implemented only after prompt/hardening evidence proves the need.
- Would require contract, parser, persistence, and UI review.

## Risks Of Prompt-Only Implementation

- Generic collapse may persist because model output can still ignore detail.
- Intent may not be inspectable by deterministic code.
- Generation and deterministic review may disagree about what the suite was
  meant to cover.
- There is no stable test surface for intent detection.
- Prompt text could accidentally become a hidden persistence contract.
- Happy-path vs edge classification may improve inconsistently across model
  calls.

## Risks Of Artifact-Backed Implementation

- Contract migration risk for existing sessions.
- Parser changes could reject currently valid requirement outputs.
- UI surface area could grow if intent display/editing is added too early.
- Review scoring could change semantics if intent is used as a scored dimension.
- Release Readiness could be accidentally coupled to intent despite being a
  release-decision signal derived from existing artifacts.
- Over-engineering risk if a full artifact is added before prompt behavior and
  deterministic helper needs are proven.

## Recommended Staged Implementation Plan

### V1.3.0 Inventory Only

- Produce this inventory.
- Do not change prompts.
- Do not change code.
- Do not change artifacts, parsers, review scoring, Release Readiness,
  execution evidence, billing, auth, rate limits, or UI behavior.

### V1.3.1 Intent-Aware Technical Requirement Prompt / Structure Hardening

Only if approved:

- Update requirement-refinement prompt and structure guidance to preserve
  executable technical details in `RefinedRequirement`.
- Add explicit happy-path vs edge/negative classification rules for requirement
  sections.
- Add intent-aware wording while preserving the existing requirement output
  contract.
- Keep changes bounded to requirement-refinement surfaces and validate with
  build.

### V1.3.2 Downstream Test Generation Alignment

Only if approved:

- Align test generation with the stronger intent-aware `RefinedRequirement`.
- Preserve existing `TestSuiteArtifact` contract unless a separate contract
  change is approved.
- Keep generation changes downstream of requirement refinement.
- Add targeted validation for API, contract, UI, unit, file, RBAC, regression,
  and happy-path classification examples.

### V1.3.3 Intent-Aware Review Context

Only if approved:

- Add bounded review context helper similar in spirit to `reviewGapPromptContext`.
- Keep deterministic review scoring unchanged unless a separate review-scoring
  milestone is approved.
- Prefer context derived from current, version-aligned artifact state.

### V1.3.4 Optional Metadata / Artifact

Only if approved:

- Consider lightweight deterministic intent metadata only after requirement and
  generation behavior prove the need.
- Define a structured artifact contract.
- Add migration/compatibility plan.
- Add parser and persistence boundaries.
- Add read-only UI display only after artifact truth is established.

## Inventory Conclusion

V1.3 is feasible without violating the Release Signal architecture rule if it is
staged carefully.

The safest first implementation branch after this inventory should target
`RefinedRequirement` quality, not `TestSuiteArtifact` behavior or review
scoring.

That first branch should harden intent-aware technical requirement refinement so
raw executable detail survives into the structured requirement artifact. Test
generation alignment should follow after the requirement artifact is stronger.
Review context should follow after requirement and generation behavior are
aligned. A deterministic intent helper or full artifact-backed implementation
should wait for explicit approval because it would touch contracts,
persistence, compatibility, and UI display decisions.
