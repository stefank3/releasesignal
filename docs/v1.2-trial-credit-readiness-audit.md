# Release Signal V1.2 Trial Credit Readiness Audit

This document audits whether the current 100-credit trial baseline is suitable for one complete Release Signal Standard Trial workflow cycle.

This is documentation only. It does not change trial duration, credit grants, credit deduction, access enforcement, billing behavior, plan-code assignment, API behavior, artifact contracts, review scoring, execution evidence semantics, Release Readiness semantics, prompts, or UI behavior.

## Current Trial Baseline

Server-owned trial and credit truth currently lives in the billing, account, wallet, ledger, and subscription paths:

- `lib/billing/ensureOrgForUser.ts`
- `lib/billing/accountAccess.ts`
- `lib/billing/chargeCredits.ts`
- `lib/chat/persist.ts`
- `app/api/me/route.ts`
- Prisma `Subscription`, `CreditWallet`, and `CreditLedger` records

Current initialization behavior:

- New organizations are still assigned `trial_v1`.
- New trial organizations receive 100 starting credits.
- New trial organizations receive a 15-day `trialing` subscription period.
- The same 100 value is stored as the starting wallet balance and as `monthlyCredits`.
- The initial grant is recorded in `CreditLedger` with reason `trial_grant`.

V1.2 packaging labels are display/planning labels only:

- `trial_v1`: current legacy/founding/private-beta trial behavior.
- `standard_trial_v1`: future Standard Trial plan code, not currently assigned by trial initialization.
- `standard_v1`: future paid/manual Standard plan code.

The current UI account badge reads server-owned state from `/api/me`. `app/chat/UserBar.tsx` displays package/credit/trial state but does not own billing, access, trial, or credit decisions.

## Credit Model

AI-backed `/api/chat` requests are gated by `ensureBillingPreconditions`, which checks subscription status, trial expiry, wallet existence, and whether wallet balance is greater than zero before the model call.

Credits are calculated after a successful model response:

```text
credits = max(1, ceil(totalTokens / 1000))
```

The model result includes prompt tokens, completion tokens, total tokens, and `creditsCharged`. `/api/chat` then calls `persistAssistantWithBillingTx`, which charges credits and persists the assistant message in one serializable transaction.

This means:

- The pre-call gate confirms the user has at least one credit.
- The exact charge is known only after the model response returns.
- A successful AI response can still fail at the billing transaction if the returned token total costs more credits than the remaining wallet balance.
- The ledger charge is idempotent by wallet, reason `chat_usage`, and request id.

## Workflow Credit Classification

| Workflow step | Current path | Credit behavior |
|---|---|---|
| Refine requirement | `/api/chat` workflow action `refine_requirement` | AI-backed. Charges token-derived credits after the model response. |
| Generate test suite | `/api/chat` workflow action `generate_tests_from_requirement` | AI-backed. Charges token-derived credits after the model response. |
| Review test suite | `/api/chat` workflow action `review_test_suite` | AI-backed. Charges token-derived credits after the model response. |
| Generate from review gaps | `/api/chat` workflow action `generate_next_batch_of_tests` | AI-backed. Charges token-derived credits after the model response. |
| Improve test plan | `/api/chat` workflow action `regenerate_suite` | AI-backed. Charges token-derived credits after the model response. |
| Export execution template | `/api/test-suites/export?format=execution-csv` | Deterministic export. No AI call. No credit charge. |
| Upload sample execution results | `/api/execution-evidence` via CSV upload | Deterministic validation and normalization. No AI call. No credit charge. |
| View Execution Evidence | UI reads persisted `ExecutionIntelligenceArtifact` | Display-only. No AI call. No credit charge. |
| View Release Readiness | `buildReleaseReadinessSummary` from persisted artifacts | Deterministic derived summary. No AI call. No credit charge. |

Legacy note: `/api/chat` still has an `ingest_execution_results` workflow action that parses execution input and charges a flat 1 credit with zero model tokens. The current upload UI uses `/api/execution-evidence`, not that legacy chat action.

## Deterministic and Free Actions

The following current V1.1/V1.2 workflow actions should remain credit-free:

- Export JSON, CSV, or execution CSV template through `app/api/test-suites/export/route.ts`.
- Upload execution CSV through `app/api/execution-evidence/route.ts`.
- Validate and normalize execution CSV through `lib/server/execution-upload/*`.
- Build `ExecutionIntelligenceArtifact` through `lib/server/execution/executionEvidenceService.ts`.
- Display Execution Evidence in `app/chat/components/ExecutionEvidenceSummary.tsx`.
- Build Release Readiness through `lib/release-readiness/releaseReadinessService.ts`.

These paths are deterministic. They do not call the model provider, do not charge credits, and do not mutate review score semantics.

## Full-Cycle Credit Estimate

The minimum Standard Trial workflow cycle contains three AI-backed actions plus one improvement action:

1. Refine requirement.
2. Generate test suite.
3. Review test suite.
4. Generate from gaps or improve test plan.
5. Export execution template.
6. Upload sample execution results.
7. View Execution Evidence.
8. View Release Readiness.

Only steps 1-4 consume credits in the intended current UI workflow.

Static code can confirm the charging formula, but not the exact charge for each action, because charge size depends on prompt tokens plus completion tokens at runtime. The response token caps are currently lower for refine/review and higher for case generation, but prompt size can vary with user input and persisted artifacts.

Conservative static estimate:

- Minimum normal cycle: 4 AI-backed requests.
- Each AI-backed request costs at least 1 credit.
- Typical V1.2 demo-sized inputs are expected to be far below a 100-credit total, but this should be verified with real telemetry.
- One retry or second improvement action adds one more AI-backed request.

Based on current code, 100 credits appears sufficient for one normal guided Standard Trial cycle with one improvement or retry, assuming demo-sized requirement input and artifacts. It is not statically guaranteed for very large pasted requirements, very large suites, repeated improvements, or unusually large prompt contexts.

## Risks and Gaps

- Exact per-action costs are not fixed constants; they are derived from runtime token usage.
- There is no static per-action credit ceiling in the audited paths.
- The pre-call access check only requires a positive wallet balance, not enough balance for an estimated maximum request cost.
- A model response can be generated before the billing transaction discovers insufficient credits for the final token-derived charge.
- Manual trial proof is still needed with a real or representative account and the intended V1.2 weak Jira-style story.
- Telemetry records token totals and credits, but this audit did not run a live paid/model workflow cycle.
- The legacy `ingest_execution_results` chat action charges 1 credit, while the current execution CSV upload endpoint is credit-free; future cleanup should avoid confusing these paths.

## Recommendation

Keep the current 100-credit trial baseline for now and do not change trial behavior on this branch.

Before any future branch changes actual trial behavior to a public 7-day Standard Trial, run a manual proof using the intended V1.2 demo story:

1. Start from a fresh trial organization.
2. Record initial wallet balance.
3. Refine requirement.
4. Generate test suite.
5. Review test suite.
6. Run one Generate from Gaps or Improve Test Plan action.
7. Export execution template.
8. Upload sample execution CSV through `/api/execution-evidence`.
9. Confirm Execution Evidence and Release Readiness are visible.
10. Record final wallet balance and per-step `creditsCharged`.

If the measured cycle plus one retry stays comfortably below 100 credits, no credit grant increase is needed for V1.2. If the measured cycle approaches 100 credits, prefer reducing per-action prompt/token cost or adding an explicit per-action cost ceiling before increasing grants.

Do not change to `standard_trial_v1`, shorten or extend trial duration, reset credits, grant more credits, or change access enforcement until that manual proof is complete and approved in a later scoped billing/trial branch.
